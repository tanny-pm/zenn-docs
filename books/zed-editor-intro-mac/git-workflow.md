---
title: "ZedでGitを扱う"
---

Zedを使い始めると、Gitとの関係がとくに密に設計されていることに気づきます。変更を加えれば即座にガターに色がつき、コミットのたびにエディタを離れる必要はなく、差分はコードと同じウィンドウに常在しています。GitをエディタのUIで制御するのではなく、エディタとGitが一体になって動くという設計思想です。

Zedのgit統合は三つの理念を掲げています。コマンドラインより速く動くこと、Gitの語彙をそのまま使うこと、そしてキーボードで完結できること。慣れたgitの操作感をそのままエディタの中で加速させる、というのが基本的な立場です。`git add -p`でhunk単位にステージしていた作業はProject Diffビューで視覚的にできるようになり、差分を眺めながら追加の修正を加え、そのままステージしてコミットする一連の流れが一つの画面で完結します。

本章では、Git Panelの基本的な使い方からhunk単位のステージング・コミット、ブランチ操作、inline blame、コンフリクトの解消、リモートとの同期まで、日常的なgitワークフローに必要な一通りをZedでどう行うかを説明します。

## Git Panelの全体像

Gitとの作業の起点となるのがGit Panelです。ステータスバーの右側にあるgitアイコンをクリックするか、コマンドパレットで「Git Panel: Toggle Focus」を実行すると開きます。

パネル上部にはアクティブなリポジトリ名とブランチ名が表示されます。その下には変更ファイルの一覧が並び、各ファイルの左端にチェックボックス、右側にはステータスアイコン（追加、変更、削除など）が添えられています。このチェックボックスがそのままステージング状態を表していて、クリックするだけでファイルをステージ・アンステージできます。パネル上部のボタンを使えばすべてのファイルを一括でステージすることも可能です。

パネルの下部はコミットエリアです。メッセージを入力して`cmd-enter`でコミットが完了します。コミット直後には「Uncommit」ボタンが現れます。これをクリックすると`git reset HEAD^ --soft`が実行され、コミットがなかったことになります。「メッセージを直したい」「もう一つファイルを追加し忘れた」という場面に手軽に使えます。

ファイル一覧のデフォルト表示はフラットな一覧ですが、パネル右上のアイコンからツリービューに切り替えるとフォルダ階層で確認できます。コマンドラインで変更を加えると、Panelはリアルタイムで状態を更新します。エディタとターミナルを行き来しながら作業しても、パネルの表示はつねに最新を保ちます。

## 差分を見る：ガターとProject Diff

ファイルを編集すると、テキストエディタの左端（ガター）にすぐ変化が現れます。追加された行には緑の縦線、削除があった箇所には赤の印、変更された行には黄色の縦線が表示されます。この小さな視覚的フィードバックだけで、現在の変更箇所を一目で把握できます。

ガターの変更指示をクリックするとhunkレベルのdiffがインライン表示されます。変更前と変更後を見比べながら、その場でコードを編集することも可能です。

プロジェクト全体の変更を俯瞰したいときは、コマンドパレットから「Git: Diff」を実行するか、`ctrl-g d`を押します。**Project Diff**と呼ばれるこのビューには、変更されたすべてのファイルとhunkが一枚の画面に展開されます。コミット前に「自分が今日何を変えたか」を通して確認するのに向いています。

![Project Diff ビュー。複数ファイルの変更が左右並列のdiffで一枚の画面に展開され、単語レベルの差分もハイライトされる](/images/zed-book/ch7-project-diff.png)
_ctrl-g d で開く Project Diff。変更箇所を眺めながらその場で追加の修正も加えられる_

diff形式はSplit（左右並列、デフォルト）とUnified（インライン表示）の二択で、Settings > Languages & Tools > Miscellaneousで切り替えられます。Word Diffが有効な場合（デフォルトでON）、行内でどの単語が変わったかも色付きで示されます。Zedのdiff表示は書き込み可能なサーフェスとして実装されているため、差分を眺めながら追加の修正を直接加えることができます。コードの確認と修正が同じ画面で完結する点は、ターミナルで`git diff`を実行する場合との大きな違いです。

## hunk単位のステージングとコミット

ステージングには大きく二つのルートがあります。Git PanelのチェックボックスはFile単位の操作に向いており、Project DiffビューはHunk単位の精密な操作に向いています。

Project Diffでhunkをステージするには、ステージしたいhunkにカーソルを置いて`cmd-y`を押します。これが`git: stage and next`に対応するコマンドで、ステージ後に自動的に次のhunkへジャンプします。すべてのhunkをまとめてステージしたい場合は`cmd-ctrl-y`（`git: stage all`）。特定のhunkを破棄したい場合は`cmd-alt-z`（`git: restore`）です。

ファイル単位での破棄は`cmd-delete`（`git: restore file`）で行えます。

ステージ済みのhunkをアンステージしたい場合は、Git Panelのチェックボックスを外すか、コマンドパレットから`git: unstage`を使います。

### コミットメッセージとAI生成

コミットメッセージはGit Panelのテキストエリアに直接入力するか、`shift-escape`でより大きなエディタを展開して書きます。72文字で自動折り返しが入るため、Gitの慣例に沿ったメッセージが書きやすい形になっています。

コミットメッセージの草案をAIに生成させる機能もあります。コミットエリアの鉛筆アイコンをクリックするか、`alt-tab`（`git: generate commit message`）を押すと、ステージ済みの差分を解析してメッセージの候補を生成します。この機能はZedのAI設定でLLMプロバイダが設定されていることが前提です（第3章参照）。生成されたメッセージはそのまま使うこともできますが、内容を確認して手直ししてからコミットするのが実際的な使い方です。

`commit_message_instructions`をagent設定に追記することで、「英語で書く」「コミットの種別プレフィックスを付ける」などのカスタム指示を渡せます。

```jsonc
// settings.json
{
  "agent": {
    "commit_message_instructions": "コミットメッセージは英語で書く。先頭にfeat:/fix:/docs:などのプレフィックスを付ける。"
  }
}
```

コミットメッセージを入力したら`cmd-enter`でコミット完了です。ステージしていない変更も含めてすべてのトラックファイルをコミットする`git commit -a`相当の動作は、`git: commit all tracked`コマンドで実行できます。

## ブランチの作成と切り替え

新しいブランチを作成するには、コマンドパレットから「Git: Branch」を実行します。ブランチ名を入力してEnterを押すと、その時点のHEADから新しいブランチが作成され、自動的にそのブランチへ切り替わります。

既存のブランチへ切り替えるには「Git: Switch」または「Git: Checkout Branch」を使います。ブランチの一覧がピッカーで表示されるので、名前を打ち始めてフィルタリングして選択します。ピッカー内に削除オプションもあり、マージ済みのブランチをその場で整理することができます。ただし現在チェックアウトしているブランチは削除できません。

Git Panelのヘッダに表示されているブランチ名をクリックしてもブランチピッカーが開くので、マウスで操作したい場合はこちらが便利です。

## inline blameとファイル履歴

コードレビューやバグ調査のとき、「この行はいつ、誰が、なぜ変更したのか」を手早く確認したい場面があります。Zedのinline blame機能は、カーソルを置いた行のblame情報をエディタ内に静かに表示します。コミットのハッシュ、著者名、相対的な時刻が一行に収まり、作業の流れを大きく妨げません。

inline blameの表示はViewメニューの「Inline Git Blame」からON/OFFを切り替えられます。キーバインドは`cmd-alt-g b`です。表示が即座に現れることが気になる場合は、Settings > Version Controlでディレイを設定できます。カーソルを置いてから2秒後に表示する、といった具合に調整すると作業中の視線の散り方を抑えられます。

![カーソル行の行末に著者名と相対時刻がグレーで表示されている状態](/images/zed-book/ch7-inline-blame.png)
_inline blame。カーソルを置いた行の変更履歴がエディタ内に静かに表示される_

ファイル全体のコミット履歴を遡りたいときは、Project Panelまたはエディタのタブを右クリックして「View File History」を選択します。コマンドパレットでも「File History」と検索すれば開けます。選択したファイルに対するコミットが時系列で一覧表示され、コミットをクリックするとそのコミットで加えられた差分を確認できます。blameで見つけたコミットの内容を掘り下げる際に、ターミナルで`git log -p`を打たなくても同様の情報が手に入ります。

## コンフリクトの解決

`git merge`や`git rebase`でコンフリクトが発生すると、Git Panelにはコンフリクト中のファイルが警告アイコン付きで表示されます。対象のファイルを開くと、コンフリクトマーカーが存在する箇所にZedがUIを重ねて表示します。

現在のブランチ（current branch）の変更は緑、取り込む側のブランチ（incoming branch）の変更は青でハイライトされ、それぞれのhunkに三つのボタンが現れます。「Use [現在のブランチ]」「Use [取り込むブランチ]」「Use Both」の三択です。ボタンをクリックするとコンフリクトマーカーが自動的に除去され、選択した側の変更だけが残ります。「Use Both」は両方の変更を上から順に保持するため、最終的に手で並び替えが必要になる場面もあります。

![コンフリクト解決のUI。HEADの変更が緑、取り込む側のブランチが青でハイライトされ、Use HEAD・Use（ブランチ名）・Use Both のボタンが表示される](/images/zed-book/ch7-conflict-ui.png)
_コンフリクト箇所にZedが重ねて表示する解決UI。ボタンをクリックするだけでマーカーが除去される_

ボタンを使わず、テキストを直接編集してコンフリクトマーカー（`<<<<<<<`、`=======`、`>>>>>>>`）を手動で消すこともできます。慣れたやり方の方が素早く解決できる複雑なコンフリクトでは、こちらが速いでしょう。

すべてのコンフリクトを解消したら、通常のフローと同じようにファイルをステージして`cmd-enter`でコミットします。

## リモートとの同期

リモートリポジトリとの同期は、Git Panelの上部に並ぶボタン、またはコマンドパレットから操作します。それぞれのキーバインドは`ctrl-g`を最初に押してから操作キーを続ける二段式です。

- **fetch**：`ctrl-g` → `ctrl-g`（`git: fetch`）。リモートの変更を取得しますが、ローカルのブランチはまだ変更しません
- **pull**：`ctrl-g` → `↓`（`git: pull`）。fetchと同時にローカルブランチをマージします。`ctrl-g` → `shift-down`でrebaseを使ったpullになります
- **push**：`ctrl-g` → `↑`（`git: push`）。現在のブランチをリモートへ送ります。`ctrl-g` → `shift-up`でforce pushも可能です

pushの際には、ブランチの`pushRemote`設定、次いで`remote.pushDefault`の順で送信先のリモートが決定されます。複数のリモートが設定されている場合は、pushの前にリモート選択のピッカーが表示されます。

ただし、ZedのGit機能が提供するのはコマンドラインの`git push`/`git pull`/`git fetch`に相当する基本操作です。GitHubでのPull Requestの作成やレビュー、インタラクティブrebase（`git rebase -i`）、サブモジュールの管理、タグ操作などはターミナルかブラウザで行う必要があります。

Zedに内蔵されたターミナル（第2章参照）を使えば、エディタを離れることなくgitコマンドを打てます。`git config --global core.editor "zed --wait"`を設定しておけば、ターミナルで起動するgitのコミットエディタとしてZedが開くので、この組み合わせは思ったより快適に機能します。

## stashによる作業の一時退避

作業中に別ブランチへ緊急に切り替えたいとき、コミットするほどでない変更をいったん片付けるのにstashが使えます。コマンドパレットから「Git: Stash All」を実行すると、ワーキングツリーの変更がすべてスタッシュに保存されます。

保存したstashは「Git: View Stash」で管理します。ピッカーが開いてスタッシュの一覧が表示され、各エントリに対してApply（適用して保持）、Pop（適用して削除）、Drop（削除）を選択できます。

stashの出番が多いと感じる場合は、Git Worktreeも検討する価値があります。コマンドパレットから「Git: Worktree」を実行すると、同じリポジトリで複数のブランチを別々のディレクトリに同時にチェックアウトできます。作業を中断して別ブランチに切り替えるたびにstashするのではなく、ブランチごとにワーキングディレクトリを分けてしまう方法で、Zedの複数ウィンドウと組み合わせて使えます。

## AIエージェントとGitワークフロー

第3章で説明したAgent PanelのAIエージェントは、Gitと組み合わせると効果が一層高まります。エージェントにコーディングの指示を出し、変更が生成されたらGit Panelで差分を確認してhunkをステージし、コミットメッセージをAIに生成させてコミット、という流れは自然に一画面で完結します。

コンフリクトが複雑な場合に「このコンフリクトの内容を解説して、どちらを採用すべきか意見を聞かせて」とAgent Panelに投げることも有効です。緑と青のハイライト表示を見ながら、AIの見解を参考にして決断できます。

また、コミット単位の粒度設計や「このPRで何を変えたかの説明文を書いて」といった作業もエージェントが得意とするところです。ZedのGit機能とAIエージェントは独立した機能ですが、隣り合って配置されているため、行き来のコストが低く実用的に組み合わせられます。

---

Zedのgit統合は、エディタとGitが一体になって動く感覚に近いものです。差分はコードと同じウィンドウに常在し、ステージングはそのdiff上でhunk単位に行われ、コミットメッセージはその流れで書かれます。

すべての操作がエディタ内で完結するわけではありません。GitHubのPRレビューや複雑なrebaseはターミナルやブラウザが速い場面もあります。日常的な変更管理とコミットはZedの中で、それ以外は気兼ねなくターミナルへ。その使い分けを前提に設計されているのが、ZedのGit統合です。
